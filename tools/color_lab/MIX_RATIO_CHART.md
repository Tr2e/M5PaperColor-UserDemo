# 同屏混色比例对照 v1（IMG_9934 后续）

日期：2026-09-09。用户要求继续推进。IMG_9934 仅证明部分色相方向改善，仍未解决灰暗/低饱和，且青色网纹更显眼。本轮用受控混色图把彩色份额与白色份额分开比较，不继续叠加未经实拍支持的照片补偿参数。

## 图的含义

400×600，顶部六块为黑、白、黄、红、蓝、绿原生颜料。下方上下两组共 40 格：

| 维度 | A 组：红＋蓝 | B 组：绿＋蓝 |
|---|---|---|
| 横向五列 | 红占彩色部分 25 / 37.5 / 50 / 62.5 / 75% | 绿占彩色部分 25 / 37.5 / 50 / 62.5 / 75% |
| 纵向四行 | 白占全部像素 0 / 12.5 / 25 / 37.5% | 白占全部像素 0 / 12.5 / 25 / 37.5% |

例如 A 组白 25%、红列 50%：白占全部像素 25%，剩余 75% 平分红蓝，因此实际为白 25% / 红 37.5% / 蓝 37.5%。不能把列标题直接理解成全部像素中的红比例。

每格 64×32、2,048 像素。同一 16×8 排序模板包含 0–127 各一次，每格包含 16 个完整模板；所有标注份额均可整除成整数色码，含四条填充边界，没有靠随机采样逼近比例。白色占 0/16/32/48 个模板像素，第一彩色颜料占剩余部分的 2/8–6/8，其余为蓝。

## 本轮能回答什么

- 同一白色行横向比较：16/17 需要多少红蓝份额，10/20 需要多少绿蓝份额，才能在面板上获得合适的色相。
- 同一彩色列纵向比较：白色增加对明度、灰白感、饱和度的实际影响，确认是否存在更好的折中。
- 原生颜料参照帮助判断当前屏幕本身的颜色表现。一次完整实拍能减少跨次照明/曝光变化的影响。

当前 IMG_9934 混合比例落在本图范围内：16 红占彩色部分约 45.6%、白约 18.6%；17 红约 38.4%、白约 17.2%；10 绿约 34.7%、白约 0.1%；20 绿约 48.9%、白约 30.8%。本图提供这些区域两侧的参照，不声称某一格精确复制原照片算法的比例。

局限：这是固定排列的原生码混合，不是照片 FS 纹理候选；不能用它的网纹优劣直接验收照片抖动。不同份额即使使用同一模板也会有不同图案。只做同屏相对选择，不从未受控手机 RGB 拟合绝对 profile；照片中的局部照明差异仍要留意。没有加入黑色变化维度，因此不能凭此完成 18 深紫和暗部映射。

## 实现与保护范围

- 新增默认关闭 `PAPERCOLOR_MIX_RATIO_CHART_ON_BOOT`。和原生旧图、人像、源色表启动入口互斥，启动前执行，A 返回正常主页。
- 使用独立 1-bit 标签 Canvas。色块通过 `papercolor_mix_chart::sample` 产生原生码，按既有 24-bit 精确触发 RGB 和无二次抖动的传输路径输出，绕过 RGB565、照片补偿、LUT 和 FS。
- 传输期间保留直接色码模式，直至 `endWrite` 完成；随后恢复显示模式和裁剪。复用既有原生图的已验证传输方式，不修改驱动波形。
- IMG_9934 照片映射/LUT/探针源码哈希逐项保持不变，照片算法的启用项也保持。只切换诊断启动入口，不写照片库、选择记忆或配置。
- 原完整源色表固件仍在 `.cache/firmware/secondary-balance-chart-candidate/`；IMG_9933 边缘修复基准也独立保留。新构建/新缓存不覆盖它们。

## 实拍后的操作

1. 拍摄整张图，均匀照明、尽量正对、保留顶部原生参照与标签。
2. 分别在 A/B 组横向比较色相、纵向比较白色影响；用“组＋白色行＋彩色列”记录优选及相邻候选，不凭一个最佳格拟合整个色域。
3. 再决定是否调整照片目标中的彩色/中性比例；为 16/17、10/20 各自检查连续过渡，同时守住 09/12/18 邻区、19 边缘和灰阶。
4. 调整后的照片固件回到原始完整 24 色表实拍验收，再考虑纹理；不把本诊断图的显示成功当作整体校色完成。
